## 1. 产品定义

TravelMindAI 是一个面向真实旅行者的智能行程规划产品。用户输入目的地、日期、预算、同行人数和偏好后，系统通过意图识别、知识检索、预算计算、多 Agent 协作与人工确认，生成一份可解释、可修改、带来源的逐日行程。

它不是“聊天机器人套壳”，也不是在线旅行社。首版只解决一个完整闭环：

**需求输入 → 信息补全 → 资料检索 → 预算约束 → 行程生成 → 冲突审查 → 用户修改/确认 → 保存与导出。**

## 2. 背景与问题

用户制定旅行计划时，需要同时处理景点筛选、开放时间、交通衔接、预算、同行人偏好和资料可信度。普通对话模型容易出现以下问题：

- 只生成“看起来合理”的文本，无法保证预算和时间约束成立；
- 用户补充条件后遗忘前文，反复询问相同信息；
- 把静态攻略与天气、票价等实时信息混在一起，缺少来源和时效说明；
- 单次生成缺少研究、规划、审查的职责分离，冲突无法被主动发现；
- 单一模型不可用、超时或结构化输出失败时，整个请求直接失败。

## 3. 产品目标

### 3.1 MVP 目标

1. 对包含最小必要信息的请求，一轮产出可审查的完整行程草案。
2. 对信息不全的请求，只追问真正缺失且会改变方案的字段。
3. 所有金额由确定性代码计算，模型只负责推荐、权衡和自然语言说明。
4. 静态旅行知识优先从管理员维护的共享知识库检索，后台保存可追溯依据；用户附件作为当前对话输入单独理解，不自动进入知识库。
5. 用 LangGraph 编排研究、预算、规划、审查 Agent，支持失败重试、返工和用户确认。
6. 接入 DeepSeek V3 系列、通义千问、Kimi、MiniMax 四类模型提供方，通过统一网关按能力路由并在故障时降级；具体模型标识由部署配置解析。
7. 提供 Vue 前端和 FastAPI 后端，完成从输入到保存/导出的端到端演示。

### 3.2 求职展示目标

项目应能在 10 分钟演示中清楚证明：

- 为什么需要多 Agent，而不是仅展示多个角色名；
- LangGraph 状态、条件边、检查点和人工确认如何工作；
- RAG 命中了哪些文档片段，回答如何引用来源；
- 主模型被故障注入后，系统如何切换备用模型；
- 预算超限、景点闭馆或时间冲突时，审查 Agent 如何触发返工；
- 前端、后端、模型、向量库和持久化如何组成一个可运行产品。

## 4. 用户与使用场景

### 4.1 目标用户

- 计划 2–5 天国内自由行、希望快速获得初稿的个人旅行者；
- 有预算、同行人、节奏、饮食或无障碍等明确约束的用户；
- 愿意上传自己的攻略、Word/PDF 材料并要求基于这些资料生成方案的用户。

### 4.2 首版数据边界

- 仅覆盖预先准备的 3–5 个国内目的地；
- 每次行程 2–5 天，1–8 人；
- 数据来自公开许可材料、官方页面整理、用户有权上传的 PDF/Word/文本；
- 天气、实时交通、即时票价等动态信息只有在接入真实工具后才能声称“实时”；未接入时必须明确标记“待核实”；
- 不抓取需要登录、绕过访问控制或无权使用的平台内容。

### 4.3 账号与角色（P0，基础已实现）

- 打开网站先显示旅行对话，首次发送提示登录/注册，成功后自动回答原问题；取消保留输入。右上角显示头像与账号名，昵称暂沿用账号名。密码6～12位，含边界；默认管理员admin/123456由部署命令初始化。

- 普通用户：已可自助注册，拥有多条独立会话并查看自己的消息；前端没有旅行资料入口。私人附件和自动逐日行程仍待实现。
- 管理员：除自己的聊天外，管理全部知识库文件、两项标签、切片和索引；不能查看其他用户私人对话附件。
- 知识库已用于公共旅行问答；未来私人附件只在所属会话使用。身份和数据归属由后端校验，隐藏按钮不能代替授权。

## 5. 核心用户故事

### US-01 创建行程

作为旅行者，我希望输入“国庆去成都 4 天，2 人，预算 6000，喜欢美食、不想太赶”，系统能直接生成符合预算的逐日行程，而不是继续问已经给过的信息。

### US-02 补全关键条件

作为旅行者，当我只说“帮我规划杭州旅行”时，系统应一次性询问日期/天数、人数、预算等关键缺口；非关键偏好可使用可见默认值，不进行无休止追问。

### US-03 基于资料规划

作为旅行者，我希望在聊天中上传路线图片或PDF/Word攻略，系统理解途经点和我的修改意图，完善当前行程草稿，并对识别不清的地方追问。用户只看读取/识别结果，不操作切片或索引。

作为管理员，我希望集中上传知识库文件，按城市和住宿/景点/餐馆分类，查看切片并管理索引，供系统回答旅行问题。

### US-04 多轮修改

作为旅行者，我希望说“第二天不要博物馆，换成亲子项目，预算不变”，系统能保留目的地、日期、人数和预算，只修改受影响部分。

### US-05 冲突发现与返工

作为旅行者，我希望系统在提交方案前主动发现预算超限、同一时间重复安排、跨区通勤不合理或资料互相矛盾，并给出调整说明。

### US-06 故障降级

作为用户，当主要模型超时、限流或返回无效结构时，我希望系统自动使用可胜任该任务的备用模型，并在不泄露内部信息的前提下完成请求。

## 6. 功能需求

### FR-01 会话与需求采集（P0）

- 登录后创建归属当前用户的独立会话并返回 `session_id/thread_id`；左侧显示可恢复的历史列表，“新建对话”保留旧会话；
- 从自然语言抽取结构化需求：目的地、出发地、开始/结束日期或天数、人数、总预算、旅行节奏、兴趣、饮食、住宿偏好、硬性限制；
- 区分 `required`、`preferred`、`defaulted` 三类条件；
- 对缺失的必要字段生成一次集中追问；
- 默认值和必要追问在聊天中说明并允许修改；结构化旅行需求只在后台维护，不固定展示需求卡或JSON；
- 日期、人数、预算等字段必须通过 Pydantic 和领域规则校验。

最小必要字段：目的地、日期或天数、人数、预算。出发地只在交通预算或跨城路线需要时必填。

### FR-02 意图识别与任务分解（P0）

系统至少识别以下意图：

- 新建完整行程；
- 修改已有行程；
- 对行程追问；
- 理解当前会话附件，以及按需查询管理员知识库；
- 只做预算估算；
- 无关或不支持请求。

Supervisor 根据意图和当前状态决定执行节点，不允许每次请求都盲目运行全部 Agent。任务计划和节点状态对前端以“正在理解需求/检索资料/核算预算/审查方案”等用户语言展示。

### FR-03 多 Agent 协作（P0）

交付分步：账号、会话与管理员资料页基础完成后启动M4-A最小文本行程智能体；M4-B接多模态附件；M4-C补独立审查、有限返工、持久暂停恢复。批量管理、文件替换和四提供方不作为智能体启动前提。下面是完整目标角色，不能理解成第一步要同时创建全部Agent；具体顺序见03第7节。

首版包含以下职责：

| 角色 | 输入 | 输出 | 是否调用模型 |
|---|---|---|---|
| Requirement Agent | 用户消息、历史状态 | 结构化旅行约束、缺失字段 | 是 |
| Research Agent | 旅行约束、检索工具 | 带来源的候选地点/注意事项 | 是 |
| Budget Tool/Agent | 人数、天数、档位和候选项 | 精确预算明细、余额/超支 | 规则为主，模型只解释 |
| Planner Agent | 约束、研究结果、预算 | 逐日结构化行程 | 是 |
| Reviewer Agent | 行程、约束、引用 | 冲突列表、通过/返工结论 | 是 + 规则校验 |
| Supervisor | 全局状态 | 下一节点、结束/追问/人工确认 | 规则优先，必要时用模型 |

Reviewer 最多触发 2 次自动返工，超过上限后向用户展示未解决冲突并请求选择，避免死循环。

### FR-04 上下文与记忆（P0/P1）

- P0：同一 `thread_id` 保存消息和图状态，刷新页面后可恢复；
- P0：修改行程时只重算受影响节点；
- P1：跨会话保存用户明确确认的长期偏好，例如饮食禁忌、节奏偏好；
- 长期记忆只能保存用户明确表达且有复用价值的信息；支持查看、修改和删除；
- 检索资料、模型推断和用户事实必须分开存储，不能把模型猜测写成用户偏好。

### FR-05 RAG 知识库（P0）

- 仅管理员可以上传、列出、预览和删除知识库文件，支持PDF、DOCX、TXT/Markdown；
- 页面仅有紧凑上传区、按城市折叠的文件列表、切片预览；移除顶部大块语义搜索和索引面板，处理状态放到每份文件旁；
- 可编辑标签与精确筛选仅为城市和类别（住宿/景点/餐馆）；另有独立文件名关键词查询，不保留审核、来源、POI标签；
- 保存原文件、正文位置、哈希及必要处理信息；正文中的来源和历史证据不因删除来源标签而丢失；
- 相同知识库范围内按content_hash去重，切片保留页码/段落定位，向量写入Milvus；
- 用户聊天可由后端按城市/类别检索共享知识库，用户无文件管理权限；
- 引用在后台可追溯，普通聊天不强制展示引用侧栏；
- 删除文档先停止检索，再清理片段、原件与向量，失败可重试。
- 切片优先保持同一景点/住宿/餐馆记录的名称、地址和价格条件关联；长记录分段保留标识，目录和孤立标题不作推荐依据，以独立题目评测质量。
- 后续批量操作支持城市组内上传预填、多选修改两标签和只重试失败文件，逐份报告结果，未提交标签保持不变。
- 后续“替换文件”先准备独立新版，完成后一次切换；失败旧版继续服务，历史回答不重写，普通同名上传不自动替换。

### FR-05A 用户对话附件与多模态理解（P0，分步实现）

- 附件绑定当前用户的当前会话，不创建知识库切片、索引或公开文件；
- 首批支持PNG/JPEG/WebP与文字型PDF/DOCX/TXT/Markdown，扫描PDF和内嵌图片单独扩展验收；不宣称支持任意格式；
- 识别路线图中的途经点、顺序和证据位置，模糊内容集中追问；地点核对与图像识别分开；
- 根据用户要求生成或局部修改未确认草稿，保留未受影响的天数、预算、人数与偏好；
- 附件识别、地点核对、逐日行程校验和草稿持久化分别验收；服务失败保留原草稿和可重试附件；
- 私人附件仅本人可见，管理员角色不自动获得读取权。
- 从消息区分“参考”“必经”“替换指定日”，不明确才追问；用途随本轮意图保存，不能仅因上传自动覆盖行程。

### FR-06 行程与预算（P0）

行程至少包含：

- 每天上午/下午/晚上安排；
- 地点、活动、预计时长、地点间交通建议；
- 当日估算和全程预算分类汇总；
- 每项建议的理由、适用偏好、引用或“待核实”标记；
- 冲突和风险提示；
- 系统假设列表。

预算分类包括住宿、城际交通、市内交通、餐饮、门票/活动、预留金。计算必须使用 `Decimal` 或整数分，不使用浮点数直接累计金额。

每次修改显示由新旧结构差异生成的摘要，并支持撤销最近一次仍有效的修改。撤销恢复修改前的行程及对应需求为新draft版本，保留历史；存在后续变化则拒绝旧撤销请求，不能覆盖新内容。首次生成没有前一草稿时不显示“撤销修改”。

### FR-07 多模型网关（P0）

- 为 DeepSeek V3 系列、通义千问、Kimi、MiniMax 提供统一适配器接口；
- 模型名、端点、密钥、超时、权重均从环境或配置读取，不写死在业务代码；
- 按任务能力选择候选池，例如结构化抽取、长文本研究、计划生成、审查；
- 综合成功率、近窗口延迟、当前熔断状态和配置权重选择模型；
- 对超时、429、可重试的 5xx、空响应和结构化校验失败执行有限重试/跨提供方降级；
- 不对鉴权失败、请求参数错误、内容安全拒绝进行盲目重试；
- 记录 provider、model alias、延迟、token、错误类别、是否降级，不记录密钥和完整敏感提示词；
- 前端只展示“服务已自动切换”级别信息，不暴露内部凭据和堆栈。

### FR-08 前端体验（P0）

首版按角色组织界面：

1. 用户聊天：左侧“新建对话”和历史列表，主区消息与附件输入；移除固定旅行需求面板和旅行资料导航。
2. 行程展示：生成后在消息中展示逐日草稿和修改摘要；完整日历工作台后续按M6推进。
3. 管理员旅行资料：上传、城市分组文件列表、切片预览；只有城市/类别两个标签。
4. 运行详情（后续演示模式）：单独受控入口，不混入普通用户主流程。

支持流式输出、失败后重试、会话恢复和响应式桌面布局。移动端只要求可读，不要求首版完成全部编辑能力。

### FR-09 保存、编辑与导出（P0/P1）

- P0：保存结构化行程，支持局部编辑和版本号；
- P0：导出 Markdown/JSON；
- P1：导出 PDF；
- 所有 AI 生成内容均为草案，用户确认后才标记为 `confirmed`；
- 首版不执行预订、支付、自动发送或修改第三方账户数据。

### FR-10 运营与可观测性（P0）

- 健康检查区分应用存活与依赖就绪；
- 生成 `request_id`、`thread_id`、`run_id` 并贯穿日志；
- 记录节点耗时、模型调用、检索条数、返工次数、错误分类；
- 提供不含敏感数据的演示运行详情；
- 支持对模型超时和 Milvus 不可用进行故障注入演示。

### FR-11 景点筛选、本地推荐与路线调整（P0/P1）

- P0：从有来源的候选景点中按城市、兴趣、明确排除项和可用时间筛选，记录入选/排除理由；
- P0：支持新增、删除、替换景点以及调整活动时间，变更后重新检查受影响日期的预算和冲突；
- P0：每天提供餐饮、住宿区域和交通建议；静态资料中的商户、价格、营业时间保留来源与采集日期；
- P0：基于区域与可靠坐标减少明显折返，输出“路线建议”；没有地图 API 时不声称路网最短、实时通勤或全局最优；
- P1：连接真实天气/地图服务后，才展示预报、路网距离与交通耗时；超出预报日期范围或工具失败时返回不可用原因；
- P1：地图展示使用经验证的坐标和数据授权；没有坐标时降级为地点列表，不能用默认 `(0, 0)` 标点。

用户未给具体日期时，可以基于天数生成第 1–N 天草案；日期相关营业规则和天气维持待核实，确认日期后再校验。

## 7. 核心业务规则

1. **事实分层**：用户事实 > 系统规则 > 有来源的检索事实 > 模型推断。
2. **硬约束优先**：日期、预算、人数、健康/无障碍、明确排除项不可被偏好覆盖。
3. **动态事实标记**：未连接实时 API 的天气、营业时间、票价和交通状态必须标为待核实。
4. **预算可解释**：任何总额都能追溯到分类和明细；模型不能覆盖代码计算结果。
5. **引用可追溯**：知识库证据包含文档/片段编号和原文位置；私人附件证据使用attachment_id及页码/图像区域，不强行生成chunk_id。
6. **记忆需确认**：长期偏好默认不从单次行为隐式推断。
7. **失败有上限**：节点重试、模型重试和返工均设置最大次数。
8. **版本防覆盖**：编辑行程时提交当前 `version`，冲突返回 409。

## 8. 非功能需求与验收指标

### 8.1 指标定义

| 指标 | MVP 目标 | 计算方式 |
|---|---:|---|
| 条件完备请求单轮完成率 | ≥ 70% | 基准集中无需追问即产出通过规则校验的草案数 / 条件完备请求数 |
| 必要字段抽取准确率 | ≥ 90% | 目的地、日期/天数、人数、预算的字段级准确率 |
| 预算计算正确率 | 100% | 确定性测试用例全部通过 |
| 引用可追溯率 | 100% | 声称来自知识库的事实均包含有效 chunk 引用 |
| RAG Recall@5 | ≥ 80% | 标注问题的相关片段进入前 5 的比例 |
| 故障注入降级成功率 | ≥ 95% | 主模型超时/429/5xx 时由备用模型完成的请求比例 |
| 首个进度事件 P95 | ≤ 1 秒 | API 接收请求到 SSE 首个事件 |
| 首个模型文本 P95 | ≤ 4 秒 | 有可用模型且不含文档解析时间 |
| 完整行程响应 P95 | ≤ 25 秒 | 2–3 天标准基准请求；在测试环境单独统计 |

以上是 MVP 验收目标，不是当前已达到的性能声明。

### 8.2 质量要求

- 后端核心领域逻辑单元测试覆盖关键分支；
- API 契约由 OpenAPI 和集成测试共同验证；
- 每个模型适配器通过统一契约测试，并在配置真实密钥时执行独立 smoke test；
- 至少准备 30 条离线评测问题，其中包含缺字段、预算超限、资料冲突和多轮修改；
- 日志、导出物和错误响应不得包含 API Key；
- 文档删除、长期记忆删除和会话删除具有明确的数据清理边界。

## 9. MVP 范围

### 9.1 P0 必须交付

- FastAPI API、OpenAPI、统一错误格式和 SSE 事件流；
- Vue 3 + TypeScript 双角色入口、用户历史对话和管理员资料页；
- 用户账号、登录和服务端角色/归属校验；
- 私人附件理解及更新行程草稿闭环（按09分步实施）；
- 需求抽取、集中追问和结构化状态；
- Research、Budget、Planner、Reviewer、Supervisor 协作图；
- 同会话短期记忆与持久化检查点；
- PDF/DOCX/TXT 解析、Milvus 检索与引用；
- 四模型提供方适配器、路由、超时、熔断和降级；
- 行程保存、局部编辑、Markdown/JSON 导出；
- 单元、集成、图路径、RAG 评测与故障注入测试；
- Docker Compose 或等价的一键启动说明。

### 9.2 P1 增强

- 跨会话长期偏好；账号与历史会话已提升为P0；
- 混合检索、reranker、查询改写；
- 真实天气/地图/交通工具适配器；
- PDF 导出；
- 行程版本对比与分享链接；
- 更完整的成本与质量仪表盘。

### 9.3 P2 探索

- 当普通 RAG 的关系约束评测确有缺口时，引入 Neo4j/GraphRAG；
- 多人协作编辑；
- 更多城市和英文；
- 预订跳转，但仍不代替用户完成支付。

## 10. 明确不做

- 真实机票、酒店、门票下单和支付；
- 宣称覆盖全国或提供生产级 SLA；
- 未接实时数据源时伪造实时天气、余票、票价或营业状态；
- 无授权抓取小红书等平台内容；
- 在首版同时建设 Kubernetes、复杂微服务、消息队列和数据湖；
- 为展示“多 Agent”而把一个简单函数拆成多个模型调用；
- 在普通向量 RAG 尚未评测前直接加入 GraphRAG。

## 11. 端到端验收场景

### 场景 A：条件完备，一轮成稿

输入：“10 月 2 日到 5 日去成都，2 人，从上海出发，总预算 6000，喜欢美食和人文，不要太赶。”

通过条件：

- 不重复追问已给字段；
- 返回 4 天结构化行程和预算明细；
- 总预算不超过 6000，或明确列出无法满足的原因和两个替代方案；
- 引用知识库资料并能打开对应片段；
- Reviewer 无阻断问题，或完成不超过 2 次返工；
- 刷新页面后能用同一会话恢复。

### 场景 B：信息缺失

输入：“帮我做一个苏州攻略。”

通过条件：一次性询问日期/天数、人数、预算；不开始虚构完整行程。

### 场景 C：多轮局部修改

在场景 A 后输入：“第三天改成亲子活动，住宿和总预算不变。”

通过条件：保留原有条件，只重跑研究/规划/审查的受影响部分，返回变更摘要。

### 场景 D：模型故障

让 Planner 的主模型固定返回超时。

通过条件：熔断/降级事件可观测，备用模型完成有效结构化输出，响应不泄露异常堆栈和凭据。

### 场景 E：文档生命周期

管理员上传一份带标题层级的DOCX和一份多页PDF。

通过条件：状态可查询、片段带页码/标题、重复上传去重、回答可引用、删除后不可再检索。

### 场景 F：增删景点与动态信息缺失

在已有方案中删除第二天下午的景点，并加入一个同城候选地点；天气服务未配置。

通过条件：仅调整相关活动与交通衔接，重新计算受影响预算；保留其他天已确认内容；展示候选来源和餐饮/住宿区域建议；天气显示“未接入/待核实”，不会以随机天气补位；没有坐标的地点不参与距离排序。

### 场景 G：双角色与多会话隔离

建立两个普通账号各两条会话和一个管理员账号。通过条件：历史只显示本人会话；新建保留旧记录；刷新/重登恢复；跨用户会话和附件访问被拒绝；普通用户没有资料导航且调用管理API返回403；管理员可管理全部知识库文件，不能访问其他用户私人附件。

### 场景 H：管理员资料页简化

上传不同城市、类别的多份文件。通过条件：只出现城市和住宿/景点/餐馆两标签；文件名与两标签组合查询准确；城市折叠计数与分页一致；顶部大型搜索区消失；文件级上传、切片、索引、重试与删除闭环保留。

### 场景 I：路线附件完善行程

在杭州旅行会话中上传路线图，要求安排到第2天。通过条件：识别途经点及有依据的顺序，模糊处追问；仅修改指定日，保留其他日和预算；新草稿及本轮结果可刷新恢复；附件未进入公共知识库；重试不重复生成版本。只有图像识别通过不算此场景完成。

## 12. 发布门槛

只有同时满足以下条件才可标记 MVP 完成：

- 第11节A～I九个端到端验收场景全部通过；
- 四提供方适配器通过契约测试，且用户配置的提供方完成真实 smoke test；
- 离线评测达到第 8 节目标或在报告中明确列出差距；
- 新环境按 README 能启动前端、后端、PostgreSQL 和 Milvus；
- 仓库不包含密钥、用户上传原文和运行时会话数据；
- 项目进度文档更新为真实测试结果，而不是计划值。
