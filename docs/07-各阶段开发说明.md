### E. 一次点击怎样走完整条链

**App.vue → api/requirements.ts → Vite代理 → FastAPI对话路由 → 抽取服务 → DeepSeek → Python合并/校验 → JSON响应 → 聊天区与需求卡片。**

前端第一次发送`previous:null`。收到成功结果后保存在当前页面；第二次发送时把这份需求放进`previous`。后端不使用一份全局变量记住所有人的旅行，因此不同页面不会串话。

| 接口 | 用途 |
|---|---|
| `GET /api/v1/requirements/status` | 只检查模型配置，不发送模型请求 |
| `POST /api/v1/requirements/messages` | 原话、previous、参考日期 → 回复、结果、状态和变化字段 |

`status=complete`表示必需旅行条件已齐，**不表示行程已生成**；`needs_clarification`表示还要补充；`unsupported`表示本页未执行该意图，旧需求保持原样。HTTP请求错误返回422，模型不可用返回503，输出连续校验失败返回502。

### F. 合并规则与边界

- 未提及的单值为null、列表为[]：保留旧值。
- 明确给出的单值覆盖；列表新增按顺序合并去重。
- `clear_fields`才代表清空；`remove_items`只删除指定的旧条目。
- 删除名称必须与历史准确匹配，匹配失败让模型修复，不能假装删成功。
- 新首尾日期决定天数；只改出发日则按已有天数推导结束日；只改天数时保留出发日并更新结束日。
- 更新后再次校验2–5天、1–8人、正数预算和日期一致性。
- 每条结果的assumptions只展示本轮推导，避免旧的人均预算等推导在新人数下误导用户。
- 页面状态只存内存，刷新即清空。尚未实现聊天消息入库、刷新恢复、归属鉴权、行程生成或SSE。
- 整个M2仍需消息持久化以及30条标注数据集和准确率验收。当前页面是M2的实际验收入口，不代表M6全部完成。

## 3. 运行时的数据顺序

主线：**命令行入口 → 需求服务 → 提示词与DeepSeek客户端 → Pydantic校验 → 汇总结果**。

1. 入口拿到你的原话、配置路径和参考日期。
2. 服务把填表规则放在`system`消息，把你的原话放在独立的`user`消息。
3. 客户端使用`ChatOpenAI(...)`创建模型对象，调用`self.model.invoke(messages)`发送消息。
4. LangChain把DeepSeek响应转换为`AIMessage`，我们只需要读取`response.content`。
5. `TravelRequestExtraction.model_validate_json()`把文本转换成旅行需求对象，并执行校验。
6. 如果答案有格式或业务错误，服务附上校验原因，让同一个模型修一次；仍失败就报错。
7. 日期齐全但天数未填时，程序按首尾日计算天数，并记录推导依据。
8. 服务自己找缺失字段，生成一个集中问题，最后把结果交还入口打印。

**模型填写内容，程序检查规则。**程序不会自动知道模型是否准确理解了所有自然语言，所以还需要真实样例评测。
JSON模式只约束输出格式，本地校验负责检查业务字段。这一接法参考[DeepSeek JSON输出文档](https://api-docs.deepseek.com/guides/json_mode/)和[思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)。

### 先读懂client.py的三步

以下是帮助理解的缩略示例，完整的配置和异常处理以源码为准：

```python
# 1. 创建一个模型对象；base_url决定请求发给谁。
self.model = ChatOpenAI(
    model=settings.deepseek_model,
    api_key=settings.deepseek_api_key,
    base_url="https://api.deepseek.com",
)

# 2. invoke表示“现在把消息发给模型”，JSON模式要求返回JSON文本。
response = self.model.invoke(messages, response_format={"type": "json_object"})

# 3. content就是模型回答，交给需求服务继续检查旅行字段。
return response.content
```

`ChatOpenAI`是LangChain的接入类名，使用DeepSeek地址和密钥时，请求仍然发给DeepSeek。后续接入兼容接口的模型可以沿用这个类；各提供方专用参数仍需要分别确认，当前`thinking`是DeepSeek参数，不是所有模型都支持。

完整代码中的`timeout`控制等待时间，`max_retries=0`关闭SDK自动重试。DeepSeek的`thinking`和`max_tokens`通过`extra_body`传递，避免框架把token参数改成另一种名字。

`http_client=http`仅用来复用并关闭底层连接，也方便离线测试；业务代码不再手写`http.post`、Authorization请求头或解析`choices`。函数末尾的异常处理把SDK错误翻译为可展示的中文。

调用方式参考[LangChain ChatOpenAI文档](https://docs.langchain.com/oss/python/integrations/chat/openai)。当前仍用`DeepSeekClient`作为业务包装类名，因为配置和专用参数只接了DeepSeek，尚未实现多提供方路由。

## 4. 几个容易混淆的地方

- `schemas/requirement.py`是数据格式，不是建表文件；不会改变PostgreSQL表。
- `null`表示用户没说；字段在JSON里直接消失则表示模型没有遵守输出格式。
- `[]`表示列表没有内容，比如用户没提兴趣。
- `total_budget`是全团人民币预算。金额用字符串保存，内部使用`Decimal`。
- `missing_required_fields`由程序计算；模型不能自己声称“信息齐了”。
- `assumptions`记录日期或金额推导依据，不是把猜测当作用户原话。
- 首版支持2–5天、1–8人。负预算、错误类型和日期天数矛盾会被拒绝。
- 最小规划条件为目的地、日期或天数、人数、总预算；出发地在当前抽取阶段不强制要求。
- 暂时只对`intent=plan_trip`生成追问。其他意图只识别和返回，尚未执行对应业务。
- 因此不能只看`missing_required_fields=[]`就判断可以规划；还要看`intent`。
- “不是两个人，是三个人”这类消息可以提取新信息，但目前不会替你更新此前的需求。
