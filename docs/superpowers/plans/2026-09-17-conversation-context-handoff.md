## 1. 用户要求与范围

用户提出的三个问题：

1. 不要用提问和输出格式校验限制正常聊天；RAG 应增强回答，资料不足时允许 DeepSeek 使用自身知识回答。
2. 生成中的内容进入可折叠过程区，最终答案单独展示，参考 DeepSeek 的交互。
3. 前文说苏州，后文推荐景点却变成杭州；西湖地址也未可靠补齐。

本方案重点解决第三项的上下文根因，并说明与第一、第二项的接入边界。地图名称匹配、地址补齐及前端过程区由主任务现有修复继续处理，不在这里设计第二套实现。

用户随后补充确认的范围：中间插入三句无关闲聊后仍能接续旅行；对话变长后完整保存原文，通过持久化摘要、近期对话和按需回查控制模型输入。两项纳入本次实施和验收，不再将长对话摘要列为未规划的后续能力。

全局约束：

- 保留主工作区已有改动，不重置、不整体覆盖相关文件。
- 复用现有历史表，不引入 Redis 记忆、向量对话记忆或新的独立状态服务。
- 对话理解错误和可选检索失败不能一律变成“重新提问”；鉴权、归属、事务、幂等、真实工具结果检查仍然有效。
- 不把历史助手回答、流式草稿或检索文章当成用户确认的旅行条件。
- 不将“知识库为空”解释为“用户问题不允许回答”。模型记忆不得冒充本轮查证的实时价格、地址、评分或营业信息。
- 正式检查读取 `backend/.env`；Python 命令从 `backend` 执行。临时验收材料按 AGENTS.md 放入 `temp/runtime`、`temp/reports`、`temp/logs`。
- 中文注释沿用同层风格；每完成两三个文件说明职责与调用关系。07 记录逐文件实现顺序，08 同步架构、接口、状态字段和验收边界。
- 不自动提交或推送，不清理其他任务的日志、上传文件、备份或服务。

## 3. 目标数据流与语义

```text
读取本会话已提交历史、旧行程和最近有效摘要
  → 超过历史预算时增量总结较早轮次；需要细节时回查原文
  → 构造统一上下文：近期对话 + 已确认旅行条件 + 最近旅行话题 + 摘要/回查原文
  → 一次本轮理解：旅行变更 / 当前提问城市 / 独立检索问题
  → 选择地图、RAG、普通回答或行程规划
  → 使用同一份近期对话与本轮证据生成最终回答
  → 短事务原子保存回答、旅行条件、话题状态、新摘要和可选行程
```

### 3.1 必须区分的三类数据

| 数据 | 例子 | 更新规则 |
|---|---|---|
| 旅行条件 | 计划去苏州、两天、预算 2000 元 | 用户明确建立、修改或清除旅行条件时更新 |
| 最近旅行话题 | 正在问杭州景点，或苏州与杭州比较 | 新旅行问题更新；无关闲聊保留，不自动改旅行目的地 |
| 外部证据 | 苏州景点原文、地图返回地址 | 本轮独立检索和核对；不反向覆盖用户意愿 |

行为示例：

| 连续输入 | 旅行目的地 | 本轮检索范围 | 下一句省略城市时 |
|---|---|---|---|
| 想去苏州 → 推荐热门景点 | 苏州 | 苏州 | 接续苏州 |
| 想去苏州 → 杭州有什么景点 | 苏州 | 杭州 | 默认接续杭州话题 |
| 想去苏州 → 杭州和苏州有什么不同 | 苏州 | 两城分别查询 | 若指代有歧义，只问必要的一句 |
| 想去苏州 → 算了改去杭州 | 杭州 | 杭州 | 接续杭州 |
| 想去苏州 → 不是苏州，是苏州市吴江区 | 苏州或用户明确的行政范围 | 吴江相关地点 | 不当成无关城市跳转 |
| 想去苏州 → 先不考虑苏州，目的地还没定 | 清除 | 按当前问题决定 | 不从更早非空字段“复活”苏州 |
| 想去苏州 → 笑话、算术、翻译三轮闲聊 → 推荐热门景点 | 苏州 | 苏州 | 恢复最近旅行话题 |

无关闲聊仍正常记录和回答，但 `conversation` 中的旅行话题默认原样保留。明确取消旅行或开始新的旅行话题才更新相应状态。“还有呢”这类泛指不强行恢复旅行：先结合最近真实对话理解；仍有多个合理指代时只问一句必要澄清。

### 3.2 对话消息组织

- 保留 user/assistant 角色，按旧到新排列。用户当前消息只出现一次，放在模型本轮消息末尾。
- 近期历史统一按内容预算裁剪完整轮次，不再每个模块各自 `turns[-3:]`、`turns[-6:]` 或截取 180 字。
- 首版可使用明确的字符预算作为近似，例如历史正文 12000 字；它不是精确 token 预算。当前消息、系统说明、状态和外部资料有各自上限，不挤入该历史预算。
- 最近一轮超过预算时，仅对其长助手回答截断并明确标记；尽可能完整保留最近用户消息，不能静默丢掉整个最近轮次。
- 页面实际展示的景点/餐馆卡片有时不在 reply 正文里，统一上下文还需保留该轮卡片顺序、名称、城市和已有地点编号，供“第一个、附近”指代；不必复制整份工具原文。
- 长期旅行条件从已提交状态取，不靠逐轮扫描历史中的城市词。检索文章、草稿和模型思考不进入已确认条件。

### 3.3 长对话保存与输入预算

完整保存与模型输入分别管理：

| 层次 | 存储方式 | 模型使用方式 |
|---|---|---|
| 完整原文 | 继续保存每轮已提交用户原话、最终回答和已有工具结果快照 | 按需回查，不每次全部发送 |
| 旅行条件与话题 | 原需求快照及 `conversation` | 每轮携带，闲聊不覆盖 |
| 较早对话摘要 | 新增可选摘要字段，带覆盖到的 revision | 与近期原文一起使用，不能代替事实原文 |
| 最近原文 | 原历史表中的连续后缀 | 保留角色和顺序，优先保留最近用户问题 |

1. 模型输入预算按“系统说明＋旅行状态＋摘要＋最近原文＋本轮证据＋当前输入＋输出预留”总体核算。历史 12000 字只是一项预算，不能视为模型总窗口。主任务根据实际配置模型核对窗口并采用保守上限；框架可用的 token 计数优先，无法精确计数时明确字符预算是近似。
2. 不每轮总结。近期原文超过历史预算时，选取即将移出窗口的连续较早轮次；使用“已有摘要＋尚未总结的新旧轮次原文”更新摘要，保留最近轮次供直接阅读。旧摘要最多 2000 字，新增原文每批最多 12000 字作为首版界限，整轮原文边界仍需保留。
3. 每个成功摘要记录 `covered_revision`，表示已处理到第几轮。新增批次必须从上次覆盖轮次之后开始，不跳过中间轮次，也不反复把已覆盖原文当新增内容。空的已保存摘要也可以有效推进轮次，不能将空文本误当失败。
4. 摘要重点保留用户选择、否定、排除原因、未决定事项、未解决问题和相关原文轮次；区分用户确认、助手建议和当时工具查询结果。闲聊可简略记录，不能挤掉旅行事实；助手以前推荐过某地不等于用户同意前往。
5. 已确认旅行条件和较新用户纠正优先于旧摘要。清除目的地后，旧摘要中的苏州只能作为历史提及，不能恢复为当前目的地。模型生成的摘要不得更新结构化旅行条件。
6. 摘要写入随本轮结果短事务提交，摘要调用期间不持有数据库事务。覆盖轮次不能超过本轮读到的已提交 revision；版本冲突时放弃本次候选摘要，不能覆盖较新会话状态。刷新、重启只读取已保存摘要，不重新调用模型总结。
7. 摘要失败不清空旧摘要、不推进覆盖轮次、不丢失已提交原文；本轮使用旧状态、旧摘要和预算内近期原文继续回答，需要旧细节时回查。若仍缺信息，不能声称已经掌握全部历史。
8. 旧会话首次接入时可能有大量未总结历史。每个新请求最多执行一次有界摘要调用，失败不在同轮无限重试；按连续批次逐步追赶，未覆盖原文仍可回查。摘要未覆盖区间与近期窗口之间存在缺口时，内部记录缺口，不能伪称摘要已覆盖到最新历史。
9. 单轮过长而无法放入摘要批次时，按该轮文本分片，只有整轮都处理成功才推进 revision；为保持首版每请求一次总结限制，可将这种超长轮次留待按需回查，不跳过它后虚增覆盖轮次。
10. 不因压缩模型输入而删除、改写已保存原文。不把会话摘要写入公共知识库、Milvus 或其他用户会话；会话删除沿用现有删除机制，不另留孤立摘要副本。

### 3.4 按需回查原文

用户问“我之前为什么排除那个景点”、引用某一轮或摘要不足以解释指代时，从本会话原始记录回查。摘要中的轮次可用于直接定位；无编号时结合当前问题里的实体与关键词查找，再带相邻轮次恢复问答关系。

- 先使用已加载的同会话历史或现有按会话查询，不为回查新增向量库或独立 Agent。
- 查询只匹配用户原话、最终回答和必要的可见卡片，不扫描密钥、内部推理或不相关账号资料；数据库查询必须绑定 session_id 并保留既有归属检查。
- 首版一次最多返回 3 个匹配轮次及各自相邻一轮，去重后总计不超过 6000 字，带 revision 和角色。优先直接指定轮次，再按实体相关程度和时间排序；结果仍不足或同名事项有歧义时明确说明或澄清，不能编造“你以前说过”。
- 原文回查与外部旅游知识检索分别标注：前者证明对话里说过什么，不能证明旧票价、营业时间现在仍然有效。
- 近期原文、摘要和回查原文重复覆盖时去重，避免相同事实多次占用输入预算。

## 4. 最小接口设计

以下为建议新增接口，不能当成当前已实现名称；主任务可在职责相同的既有模块内实现，避免重复类。

### 4.1 数据类型

建议在 `backend/app/schemas/requirement/chat.py` 附近定义以下小模型，复用 `RequirementUpdate`：

```python
class ConversationState(BaseModel):
    topic_cities: list[str] = Field(default_factory=list)
    topic_places: list[str] = Field(default_factory=list)

class HistorySummary(BaseModel):
    text: str = Field(default="", max_length=2000)
    covered_revision: int = Field(ge=0)

class TurnUnderstanding(BaseModel):
    requirement_update: RequirementUpdate
    destination_action: Literal["keep", "set", "clear"] = "keep"
    topic_action: Literal["keep", "set", "clear"] = "keep"
    query_cities: list[str] = Field(default_factory=list)
    retrieval_query: str = ""
    conversation: ConversationState
```

含义：

- `destination_action` 专指旅行目的地；`set` 必须有本轮明确意愿和有效 destination，`clear` 表示用户明确取消。不能由搜索命中内容触发。
- `topic_action` 专指最近旅行话题。普通闲聊为 keep，由程序保留旧 conversation，不用模型随手返回的空列表覆盖；set 使用本轮新旅行话题，clear 只用于明确清除。两种 action 分开，支持咨询杭州而保留苏州旅行目的地。
- `requirement_update` 延续已有日期、预算、人数等更新规则。普通知识咨询不应将所有新提到的地点写入旅行目的地。
- `query_cities` 是当前问题范围，允许为空或多城市；空值表示地点未知或本题无需地点。
- `retrieval_query` 是当前输入的独立表达，包含接续的地点/偏好，不补编预算、天数、距离等用户没说过的条件；无需检索时为空。
- `conversation` 是本轮完成后的最近旅行话题状态，不是所有聊天话题。无关闲聊保留旧值；明确新旅行话题或取消时才更新，也不是事实证据。

在 `RequirementChatResponse` 新增可选 `conversation: ConversationState | None = None`，复用现有 `response_json` 原子保存，无需新建表。旧记录缺字段仍可解析；08 文档记录这一 JSON 契约变化。

显式空列表与 None 必须区别：None 表示旧版没有保存话题字段；已保存的空列表表示当前已清空，不能回退更早状态。

再新增可选 `history_summary: HistorySummary | None = None` 到 `RequirementChatResponse`。只在摘要实际更新的轮次写入新摘要，其他轮次保留 None 以避免每轮复制；恢复时取当前会话最新一个非 None 摘要。`text=""` 且有覆盖轮次仍为有效记录，与 None 不同。字段级类型、默认值、语义、覆盖版本检查和旧记录兼容均写入 08 文档；不新增数据库列或迁移。

### 4.2 统一上下文函数

建议新增 `backend/app/services/chat/context.py`，只负责纯数据整理：

接口签名：`build_history_messages(turns: list[SavedRequirementTurn], *, max_chars: int = 12000) -> list[dict[str, str]]`。

实现算法明确为：从最新轮开始计算本轮用户消息与助手可见内容长度，累积到预算；保留能容纳的连续后缀，再按 revision 升序展平为 user/assistant 消息。最新轮单独超长时按 3.2 的规则处理，不跳过最近轮去选更旧内容。

不要把外部资料当成新的真实用户要求或 system 指令。将检索资料作为明确标注“不可信参考内容”的独立块加入模型输入。旧助手文字只用于理解对话，不证明新回答的事实正确。

### 4.3 本轮理解的接入

复用需求抽取那次模型调用，扩展为带统一上下文的本轮理解；不要另加城市识别、检索改写、路由三次串行调用。摘要仅在超过预算或处理既有积压时按 3.3 增加一次有界调用，不成为每轮固定前置步骤。

- 聊天入口使用新的本轮理解结果。
- 保留旧需求提取 API/CLI 的输出契约；需要时通过内部共用消息构造或适配函数复用，不强迫独立接口返回聊天状态。
- 地图分流必须获得当前轮理解后的查询城市与统一历史，而非只拿旧 previous.destination。
- 模型格式失败可有限修复一次；仍失败时直接使用原始连续对话生成自然回答，本轮不提交推断不可靠的字段变更、不生成猜测城市的地图卡片。
- 这种失败不应再次以旧目的地拼出可能错误的新查询；优先保留旧结构化状态并让自然模型理解原话。

### 4.4 摘要与回查接口

在 `chat/context.py` 保留纯预算裁剪和数据整理；摘要生成放在主任务已有 `chat/conversation.py`，复用 ModelClient。建议接口：

- `summarize_history(previous: HistorySummary | None, turns: list[SavedRequirementTurn], model: ModelClient) -> HistorySummary`：接收程序选定的连续批次，只让模型生成摘要文本；`covered_revision` 由程序从实际完整处理的最后轮次赋值，不能相信模型自报进度。
- `recall_history(turns: list[SavedRequirementTurn], query: str, revisions: list[int] | None = None) -> list[SavedRequirementTurn]`：只处理调用方已获授权的本会话数据，按 3.4 匹配及限量；随后统一转换成带轮次的原文块。

摘要提示明确保留“谁提出、是否确认、否定条件、未决问题、原文轮次”，禁止把外部正文中的指令当要求。新生成摘要作为派生上下文提供，不能提升为 system 指令。摘要输入输出超限或模型错误时调用方保留旧摘要；不通过截断摘要文本来伪装成功，因为截断可能丢掉否定条件。
