## 1. 改造结论

系统分为两个入口、两条文件处理流程：

| 对象 | 管理员知识库 | 用户对话附件 |
|---|---|---|
| 用途 | 维护可供旅行问答使用的公共旅行知识 | 表达当前对话的路线、偏好或行程修改意图 |
| 入口 | 管理员的“旅行资料”页面 | 聊天输入框旁的附件按钮 |
| 可见范围 | 管理员可管理全部知识库文件，不按某一上传管理员分割列表 | 仅所属用户、所属对话；管理员角色不自动获得访问权 |
| 处理方式 | 上传、解析、城市/类别标注、切片、索引 | 读取文字或图像、提取地点和顺序、核对、更新当前草稿 |
| 存储 | 复用 documents、document_chunks、document_jobs 和 Milvus | 新建 conversation_attachments，关联 sessions；结果随对话轮次保存 |
| 是否进入公共向量库 | 是 | 否 |
| 用户是否看技术操作 | 仅管理员看切片、索引状态和失败重试 | 显示“已上传、正在识别、待确认、处理失败”等业务状态 |

“去掉旅行需求”指移除前端固定需求面板。后台继续保存、校验和合并旅行条件；必要的追问放在聊天里，不能因面板消失而丢失预算、人数等约束。

## 3. 方案选择与边界

| 方案 | 收益与代价 | 结论 |
|---|---|---|
| 只隐藏页面和重排组件 | 改动小，但无法建立真实的用户隔离，附件仍走错流程 | 不能满足本次目标 |
| 现有单体内按账号、知识库、对话附件拆分职责 | 复用现有解析、历史、预算和草稿能力，分步验证 | 推荐 |
| 拆管理员应用/用户应用及独立后端服务 | 可独立部署，但引入额外认证、接口和部署维护 | 当前不需要 |

推荐继续使用一个 Vue 项目和一个 FastAPI 应用，前端按角色提供不同入口，后端强制授权。首步只做两种角色 `admin/user`，不引入权限配置平台、多租户、组织、角色关联表或新的状态管理框架。

以下列出已实现的基础选择和后续附件目标：

- 首页先显示对话输入，首次发送才弹出登录/注册，成功后自动回答原问题；右上角保留主动登录入口，登录后显示首字母头像与账号名。普通注册只得到user角色，密码统一6～12位；管理员由显式部署命令首次创建admin/123456，重跑不重置；找回密码仍未实现。
- 类别单选：住宿、景点、餐馆。无法确定的文件保留空值，并显示“未分类”；它不是第四个业务标签。混合资料由管理员选择主要类别，必要时在入库前拆成独立文件。
- 先完成 PNG/JPEG/WebP 图片与现有文字文档的附件闭环，再支持扫描 PDF 和 DOCX 内嵌图片；音视频、压缩包、任意二进制格式不在首批承诺中。
- 只增加一个通过能力实测的视觉模型接入；既有文本模型继续负责已验证的文本任务，不为本次目标提前完成四提供方网关。具体视觉模型待实现阶段按路线样本验证后确定。

### 4.2 页面结构

页面只设三个主要区域：

1. **上传**：顶部紧凑工具栏支持多选，上传结果逐份显示；默认复用上传后自动切片/索引。
2. **资料显示**：左栏放文件名查找和两项筛选；下面按城市折叠分组。每个文件显示名称、类别和一行处理状态。
3. **切片预览**：右栏显示当前文件名、两个可编辑标签、分页切片；“查看原文”“重试处理”“删除”等放在文件级操作区。

索引进度收进文件行和选中文件的简短状态，不再出现第二个大型后台处理面板。切片尚未生成时显示具体阶段，失败时在原位置重试。空列表、筛选无结果、未选择文件使用不同提示。

城市分组由后端根据同一组文件名/城市/类别筛选条件统计数量；点击展开再分页加载该城市文件。不能只把当前一页文件在浏览器分组，导致城市数和文件数不完整。城市比较使用统一规范化规则，保留现有“无法确定则留空”的原则。

### 4.3 标签与引用的区别

仅 `city/category` 作为可编辑业务标签和筛选项；原文件名、上传时间、大小、处理状态属于文件信息。正文中原有来源链接、页码和历史回答的证据快照继续保留，用于核对事实，不作为来源标签重新出现在界面。

移除的是**资料级 POI 标签**。高德定位返回的地点编号、坐标和匹配结果仍由地图业务使用，不能随资料标签一起删掉。

## 5. 用户聊天与历史会话

- 左侧顶部为“新建对话”，下面列出当前用户历史，按最近更新时间排序，可按今天/近七天/更早作显示分组。
- 点击历史只读取该会话的消息、附件结果和草稿，不重跑模型或索引。列表分页，刷新/重新登录后仍能找到历史。
- “新建对话”创建独立空会话并切换过去，保留旧会话。创建按钮禁用至请求完成，避免连点生成重复空会话。
- 默认标题“新建对话”；首次成功发送后用首条消息的简短文本生成标题，不为标题额外调用模型。
- 中间为聊天区，移除右侧“当前旅行需求”、需求JSON及其底部说明；必要的条件补问和修改摘要直接显示在消息中。
- 原“重新开始”改为左侧“新建对话”；原“重新读取”作为读取失败时的“重试加载”，正常状态无需常驻。
- 用户上传文件后，附件出现在输入区并随消息发送。上传本身不立即修改行程，避免误选文件触发规划。
- 有行程时以消息内行程卡片展示逐日安排和修改摘要，并可撤销最近一次行程修改；历史版本仍可回查。未生成时不显示空的永久右侧面板，撤销规则见12.2。
- 切换会话时清理本地需求/附件选中状态。正在发送可先禁用切换；异步结果仍按 session_id 归位，不能落入后来打开的对话。退出账号清空界面和浏览器会话缓存。

## 6. 权限与知识使用

| 操作 | 普通用户 | 管理员 |
|---|---|---|
| 新建、列出、继续自己的会话 | 允许 | 允许 |
| 读取别人的会话、草稿、附件 | 禁止 | 禁止；本轮没有客服代查功能 |
| 上传和读取自己当前对话的附件 | 允许 | 允许 |
| 查看旅行资料导航及管理页面 | 隐藏 | 允许 |
| 列表、预览、修改、删除知识库文件 | 禁止 | 允许，覆盖全部知识库文件 |
| 标签、切片、索引、后台任务操作 | 禁止 | 允许 |
| 聊天中使用公共知识库得到推荐 | 后端按需检索 | 后端按需检索 |

后端从登录态解析 user_id 和 role，不能相信请求体、查询参数、浏览器存储或客户端传来的 owner_id。所有旧资料管理路径也必须加管理员校验，不能仅增加 `/admin` 新路径而留下旧接口绕过。

未登录返回401；非管理员访问管理操作返回403；跨用户会话/附件编号统一视为不可见并返回404。文件读取通过受保护接口，存储目录不直接作为静态目录开放。

知识库作为共享资源使用服务端固定 `knowledge-base` 范围；`uploaded_by` 记录上传管理员，不决定谁可以检索。用户的 user_id 用于私人会话授权，不能直接替代知识库检索 owner_id，否则用户只能查到空库。Milvus 查询与 PostgreSQL 原文回查必须使用同一知识库范围。

## 7. 用户附件怎样完善草稿

以“上传杭州徒步路线图，并把它安排到第二天”为例：

先结合消息区分附件用途：“仅供参考”“必须经过这些点”“替换指定日”。用途不明时集中追问，不因上传自动覆盖草稿；已明确“安排到第二天”时不重复确认。用途是本轮消息的意图，同一附件后续可以换用途，不永久写死在文件上。

1. 校验登录、会话归属、类型和大小，将原件保存为当前会话附件，返回 attachment_id。
2. 用户发送消息及 attachment_ids；先检查消息幂等性与 expected_revision，再核对所有附件属于当前会话。
3. 对文字文档提取正文；对路线图读取地名、路线连线/箭头和可识别的顺序。输入内容视为资料，里面出现的指令不能覆盖用户要求。
4. 输出有结构的识别结果：城市、按顺序的途经点、页码/图像区域依据、无法确认的名称和顺序。模型置信度只能辅助判断，不等于地点核验通过。
5. 用现有地图能力核对同城地点、重名候选及坐标；图中连线不等于实际可通行步道，未确认时不能声称精确里程、实时耗时或安全通行。
6. 地名/方向不清晰时在聊天中集中追问，并保存可恢复的待确认结果。清晰内容按用户指令形成第2天的修改建议。
7. 有草稿时局部修改第2天，保留其他天与硬约束；没有草稿时创建未确认草稿，必要条件不足则继续补问。单日路线可以作为2～5天旅行中的一天，不默默扩大整体行程范围。
8. 校验活动顺序、时间、预算与来源；保存新需求/行程版本及本轮结果，回复“识别了哪些点、调整了哪里、哪些仍待确认”。

识别结果建议契约：`city`、`waypoints[{name, order, evidence, matched_place, needs_confirmation}]`、`warnings`；`evidence`包含附件编号及页码/区域。生成的 `itinerary_json` 需先定义逐日活动结构，至少含日期或第几天、顺序、地点、时长、交通说明和依据；不能仅以“JSON对象”校验冒充行程业务校验。

知识问答可调用公共知识库，补充酒店或餐馆建议；附件识别和纯条件修改不强制调用Milvus。长文按页读取或按输入预算分批处理，是模型读取策略，不生成管理员知识库切片和向量。

视觉入口需要明确支持的图片类型、文件/页数/像素及模型输入限额。首批单文件上限建议沿用20 MiB，其余限额按选定服务实测确定；文件过大或不支持时明确告知，不能悄悄截断后声称全部读完。视觉服务未配置/失败时保留附件与当前草稿，并提供重试；纯文字聊天应继续可用。

## 8. 数据、接口与一致性

### 8.1 最小数据改动

当前账号、会话与资料逐字段数据字典见[08第7.5节](./08-架构设计说明.md)；附件和文件替换目标字段见08第12节。

- 新增 `users`：账号、密码哈希、角色、启用状态和时间。
- 新增 `auth_sessions`：服务端登录态；与旅行会话 `sessions` 含义不同。
- 扩展 `sessions.user_id` 外键及用户历史索引；现有标题、状态、thread_id 继续使用。
- 新增 `conversation_attachments`：归属会话、原件定位、文件信息、读取状态与结构化识别结果；通过会话关联用户，不冗余存一份 owner。
- 扩展 `documents.category/uploaded_by`；city保留；source/review_status/poi_id退出现行管理契约，后续迁移清理。
- 保留 `requirement_turns`：成功轮次的 response_json 增加可选附件快照及 itinerary_id/version；旧记录按缺省值读取。
- 保留 `travel_requests/itineraries`：新版本写入与对应对话轮次在同一事务提交。仅理解附件、尚待追问时允许只存轮次与识别结果，不伪造完整行程。

模型/地图调用在事务外；最终以会话行锁重新核对 expected_revision 和草稿基础版本，再提交。重试沿用同一 message_id，正文和附件ID列表都必须相同；相同ID、不同附件返回409。成功重试返回已存结果，不重复调用模型或生成行程版本。识别中的服务中断需标失败可重试，不能永久停在processing。

### 8.2 接口状态（均以 /api/v1 为前缀）

认证、`GET/POST /sessions`、旧会话/草稿接口及管理员资料旧路径和`/admin`别名已写入源码。实际城市计数为`GET /documents/cities`，游标列表为`GET /documents/page`（`/admin`别名同效）；下表的附件、撤销、批量标签和替换接口仍是目标，不应当作可调用地址。所有管理旧路径也校验管理员。

| 方法与路径 | 用途与权限 |
|---|---|
| POST /auth/register、POST /auth/login、POST /auth/logout、GET /auth/me | 登录、撤销当前登录态、读取当前账号角色 |
| GET /sessions?cursor=&limit= | 只列出当前用户会话，按updated_at/id倒序稳定分页 |
| POST /sessions、GET /sessions/{id} | 复用现有创建/读取，注入用户归属 |
| GET/POST /sessions/{id}/requirement-messages | 保留现有地址，扩展附件ID及结果；不为去掉需求面板强行改接口名 |
| POST /sessions/{id}/attachments | 私人附件上传，仅保存原件和待处理记录 |
| GET /sessions/{id}/attachments/{attachment_id} | 读取状态与识别结果；原件通过同归属校验的/content子路径读取 |
| POST /sessions/{id}/drafts/undo | 显式撤销最近仍有效修改；operation_id、expected_revision、expected_itinerary_version及目标修改编号均需校验 |
| GET /admin/documents/cities?q=&city=&category= | 管理员城市分组和筛选后文件数量 |
| GET /admin/documents/page?q=&city=&category=&cursor=&limit= | 指定城市内文件分页；q仅查文件名，未标注城市用约定的空值筛选表示 |
| POST /admin/documents、GET/DELETE /admin/documents/{id} | 复用上传、详情、删除业务，管理员授权 |
| PATCH /admin/documents/{id}/metadata | 只接受city/category，未知字段拒绝 |
| POST /admin/documents/metadata-batch | 后续增强：只改选中文件的明确提交标签，逐份反馈 |
| POST /admin/documents/{id}/replacements | F阶段：准备新版并按12.5规则切换，普通同名上传不触发 |

## 12. 用户接受的五项补充（2026-09-15，按项标注状态）

### 12.1 附件用途：参考、必经、替换

优先从自然语言判断，不增加必填表单。“参考这种轻松程度”只提供偏好；“这些点都要去”产生可追溯的必经约束；“替换第二天”只作用于指定日。遇到预算、时间或路线不可行时说明冲突并追问，不因为附件写了必经就跳过校验。

验收：同一附件分别用于三种消息，产生不同处理；未说明用途时只提出必要问题；模型不能把参考地点全写成硬约束。用途和目标日期随轮次快照保存，用户后续纠正时按新轮次更新。

### 12.2 修改摘要与撤销

每次生成新草稿后，用简短消息说明增加/移除了哪些活动、影响哪些日期及预算是否变化。摘要由新旧结构差异生成，不能只信模型自述“其他都没变”。

首版撤销只处理最近一次仍有效的行程修改：提交当前会话revision、当前草稿版本和本次操作ID；后端核对后将修改前行程及其对应需求恢复为**新的未确认版本**，保留旧版本和聊天记录。没有更早草稿的首次生成不提供“撤销修改”；后续已有新需求/行程变化时旧按钮失效，返回冲突而非覆盖新内容。撤销不重新调用模型，不重复写入版本，不自动恢复confirmed状态。

验收：修改后摘要与实际差异一致；撤销恢复活动、预算和对应需求；刷新一致；重复提交不增加版本；旧页面撤销被409拒绝。基础实现纳入M4-A，附件修改复用同一规则。

### 12.3 以地点记录为单位核对切片质量

优先让一条景点、住宿或餐馆记录内的名称、地址、价格说明保持关联。短记录尽量完整保留；超过当前800字符上限时仍分段，并保留原有标题路径/记录标识，不能无限加大切片。不将重复目录、孤立标题或纯来源说明作为独立推荐依据；原件和来源定位保留。

先选住宿/景点/餐馆各若干实际样本核对召回，只有发现拆分确实损害关联时再修改chunker。切片正文和原文字符范围必须一致，不直接拼入上下文破坏start_char/end_char；如果改变Embedding输入拼接策略，需要新策略版本和独立索引验收。新旧切片不可混用；在副本上验证重建后再切换，历史证据快照不重写。

验收：地点名、地址、价格条件能指向同一记录；同名异地内容不串；未知价格不变成免费；保留独立问题集检查召回和回答忠实度。该项是M3质量改进，不以“片段更多”或“索引100%”作为质量结论，也不无限拖延M4-A。

### 12.4 管理员批量操作

- 在城市组内上传时默认填入该城市；明确的文件内容与所选城市冲突时提示，不静默覆盖。
- 多选文件统一修改城市或类别。批量请求只更新明确提交的标签，未提交字段保持；显式空值才表示清空。
- 批量重试只选失败或中断任务，已完成文件不再次向量化；每份返回成功/失败结果，不用整批失败掩盖部分成功。

验收：仍只有两个标签；未选文件不变化；城市/类别组合准确；上传继承不掩盖冲突；重试不重复收费处理完成文件。沿用单文件权限、任务和幂等机制，不新增批处理平台。可在C后补充，不阻塞智能体接入。

### 12.5 文件替换与新旧知识切换（F，后续增强）

管理员对某文件选择“替换文件”，系统保存独立新版原件并准备正文、切片和索引；**旧版持续可检索，新版准备完成并核对后一次切换**。新版解析或索引失败时保持旧版，允许单份重试。普通同名上传不能自动触发替换；同名不同内容先由管理员明确决定。

新旧文件使用不同document_id/chunk_id，通过同一资料组关联。一次只能有一个当前版本；新版未激活及被替换旧版的向量即使仍存在，也必须在检索前筛掉并在原文回查时复核。两个管理员同时替换时锁当前版本并校验预期版本，只允许一个成功切换。

旧版原件与片段暂保留供回查，不在切换时立即物理删除；历史聊天沿用当时证据。相同内容保持现有范围内哈希去重，不为“替换”复制相同文件。目标字段/索引见08第12.9节，具体迁移在F单独实施。

验收：新版完成前只命中旧版，切换后新问答只使用新版；失败旧版正常；并发替换不出现两份当前版本；历史回答不改变。复用后台处理，暂不做复杂版本管理界面。
